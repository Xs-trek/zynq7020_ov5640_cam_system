# v0.2.0 发布说明

日期：2026-11-16

v0.2.0 配套的 PL 是 R10（硬件溯源标识 `r10-rc2`），对应
`hardware/v0.2.0/zynq7020_face_accel_r10_rc2_20261105.xsa`。PL 寄存器接口在 R9 的基础上扩展，
R9 比特流仍能运行，只是走拷贝路径。

## 自 v0.1.1 以来的变化

### 检测链路

- **零拷贝检测路径。**
  - 采集缓冲来自设备树保留区，通过 `VIDIOC_EXPBUF` 导出为 dma-buf，交给加速器驱动导入。PL 直接读同一块内存，PS 不再为检测复制帧。
  - 只有 JPEG 等 CPU 消费者需要像素时才 `memcpy` 到缓存池；没有 CPU 消费者时不复制。
  - 回退分三层，任何一层失败都落回拷贝路径：驱动没有 dma-buf 输入能力；配置 `face.zero_copy=0`；运行中导入或直通作业失败。
  - 打开直通后的第一帧做一次自检：同一帧分别走直通和拷贝路径，逐字节比较输出，不一致就退回拷贝路径。
  - `/api/status` 的 `detector_input` 报告当前路径（`direct` 或 `copy`）。
- **R10 加速器驱动 UAPI v2。**
  - v1 的 `GET_INFO`、`RUN`、`RESET` 保持二进制兼容。
  - 新增 4 个 ioctl：`GET_CAPS` 报告版本、`HW_REVISION`、权重 SHA-256 和能力位；`IMPORT` 导入 dma-buf，句柄随文件描述符释放；`SUBMIT` 提交作业；`WAIT` 取结果。
  - 版本协商：新应用拿到 `ENOTTY` 就退回 `RUN`，所以只换应用或只换驱动时都能工作。
  - 等待不再被普通信号打断；中断处理只看 `IRQ_STATUS`；输出缓冲改为可缓存的流式映射。
  - 驱动源码可以经一层内核桩（`tests/kshim/`）在主机上测试。
- **CPU 检测候选改为可选。** CMake 选项 `CAM_SYSTEM_ENABLE_CPU_DETECTORS` 默认关。关闭时不编译 ncnn、UltraFace、libfacedetection，产品只用 PL 检测。

### 控制与跟踪

- **按检测结果触发控制节拍。**
  - 每帧仍只有一个控制节拍。触发时刻改为两者中较早的一个：本帧检测发布，或截止时刻（帧的采集时间加 `control.deadline_ms`，默认 24 ms）。
  - 迟到的检测不丢弃，作为延迟测量喂给估计器。
  - ISP 写入晚于下一帧时计入 `isp_slips`，视口时间线按 N+3 帧生效登记。
- **跟踪参数按人体运动范围设定。**
  - 路径带宽从 ω 6 rad/s、jerk 7200 px/s³ 提高到 ω 8、jerk 18000，依据是检测延迟从 3 帧降到 0 帧。
  - 速度上限从 450/300 px/s 提高到 780/540 px/s，取三维人体运动模型下人脸画面速度的 P99，单帧最大步长相应为 26/18 px。
  - 加速度上限保持 1800 px/s²，由整数命令二阶差分 ≤ 3 的平滑约束决定。
- **边界刹车。** 刹车先往前看一帧，并留一帧余量，按正常的加速度和 jerk 上限把窗口停在平移极限上。原来的保护只看当前状态，边缘急停时会撞上极限。
- **数字轨迹记录。**
  - 配置项 `tracker.trace`（`CAM_TRACKER_TRACE`）默认关闭。
  - 打开后每个控制节拍写一行 CSV：帧号、检测框、采纳的观测、Kalman 状态、参考轨迹、路径和 ISP 偏移，只有数字，没有图像。
  - 文件必须在 `/tmp/` 下，权限 0600，满 16 MiB 停止。
  - 这些数字是真实画面里的人脸坐标，记录和使用前应取得被摄者同意。

### 系统与运行

- **launcher 权限分离与守护。**
  - `cam-launcher` 以 root 启动，fork 后切到专用用户 `camsys` 再启动 `cam_system`。
  - 设备访问经 `video` 组和 udev 规则 `60-cam-system.rules` 授予。
  - 应用异常退出后，launcher 退避重启（1 s 起翻倍到 30 s）；退出码 0 和配置错误不重启。
  - 可选开机自启，默认关闭。
  - 新增配方 `sudo-policy`，设置 `secure_path`。
- **传感器电源管理。**
  - OV5640 只在有打开的子设备句柄或正在出流时上电，识别后即断电。
  - 相机关闭时传感器不出流。每段出流最长 `capture.max_stream_min` 分钟（默认 20），到时自动关相机，`cam_off_reason` 报告 `stream_limit`。
- **开相机重新初始化。** 传感器从软件 standby 唤醒后不恢复 DVP 输出，所以每次开相机都做硬件复位并重写完整寄存器表，再起流。
- **采集自愈。** 4 s 没有好帧就重建流，重建 3 次仍失败以退出码 70 退出，由 launcher 重启。另有看门狗：采集线程卡住 15 s 时同样退出。
- **配置文件。** 运行配置统一在 `/etc/cam_system.conf`（`config/cam_system.conf`），同名环境变量优先；未知键和越界值在启动时报错。
- **状态诊断字段。** `/api/status` 新增检测器健康、DVP 帧和坏帧计数（本次运行）、ISP 迟写次数、版本和硬件身份等字段，见 `docs/CAM_SYSTEM_SOFTWARE_TOP_LEVEL_SPEC.md`。

### 页面与推流

- **MJPEG 帧尾。** 分隔符和下一分片的头紧跟 JPEG 发送，浏览器不必等下一帧才显示当前帧。在本机 Chromium 回环上，显示延时 p50 从 37 ms 降到 4 ms；手机 WebView 上没有单独测量。
- **页面码率开关。** 默认行为不变，只影响页面显示，采集、检测、跟踪仍每帧处理：
  - `jpeg.quality`：20–95，默认 70；
  - `stream.max_fps`：0–30，默认 0 不限，按 30/n 档位降帧。
- **页面副本。** 手机页面副本放在 `frontend/gimbal/index.html`，去掉了无效的帧率计数和变焦显示。

## 板测数值

板子为 Zynq-7020 + OV5640，配 R10 比特流。下表的 R9 数值是 v0.1.1 时的记录（空场景），单位毫秒，格式为中位数 / 最大值：

| 指标 | R9 | R10 零拷贝 | R10 拷贝 |
|---|---|---|---|
| PL 推理 | 26.13 | 22.2 / 22.2 | 22.1 / 22.1 |
| 检测总耗时 | 28.94 | 22.7 / 23.4 | 24.1 / 24.2 |
| PS 侧耗时 | — | 0.6 / 1.3 | 2.0 / 2.1 |
| 结果延迟（采集到发布） | — | 22.9 / 52.2 | 28.1 / 37.3 |

- **稳定性：** 600 s 长稳（约 1.8 万帧），错误计数增量为 0。
- **恢复：** 10 轮 `kill -9` 之后每轮都恢复，内核没有 Oops。
- **控制节拍：** 跟踪中 `on_detection` 30/30，`isp_slips` 为 0，ISP 写入余量平均 6.05 ms、最小 4.44 ms。
- **跟踪参数对比：** 在板上录了两段跟踪轨迹，用同一段观测分别回放给旧参数和新参数的控制器：
  - 新参数的跟踪误差 RMS 小 11–25%，水平加速段的落后少 10–16 px；
  - 没有帧超过 26/18 的单帧上限，二阶差分 ≤ 3、三阶差分 ≤ 4 都满足；
  - 回放与板上实录的误差差别不超过 2%。

## 已知限制

- **网络：** HTTP/WebSocket 没有认证和 TLS，只适用于可信隔离局域网。服务按单个手机客户端设计，多客户端只做了基本支持。
- **Wi-Fi：** 板子只做 Wi-Fi 客户端，没有热点模式。USB 网卡在部分环境下会间歇丢包。
- **跟踪：** 人横向快速起停时，加速度可能超过 1800 px/s² 的路径上限，这时窗口会明显落后。
- **变焦：** 板端没有变焦。`/api/zoom` 只为兼容旧前端保留，`status` 不含 `zoom`。
- **存储：** rootfs 在内存里，日志、轨迹文件和板上改过的配置，断电后都会丢失。
- **复现范围：** 仓库不含 PL 的 RTL/HLS 源码，XSA 只能用于平台重建，不能重新综合 PL。
- **模型：** SCRFD 和 UltraFace 的 CPU 候选模型不随仓库发布，见 `docs/MODEL_ASSETS.md`。
